# Self-Review: Архитектурные решения

## Контекст разработки

Проект выполнен за **3 дня** в режиме "быстрого прототипирования" с жесткими ограничениями:
- **Бюджет API:** Бесплатный tier OpenRouter (Solar Pro: 16k context, rate limits)
- **Цель документации:** Обеспечить полную прозрачность архитектурных решений и логики работы агента для упрощения технического аудита кода.
- **Приоритет:** Работающая система > теоретическая идеальность

## Ключевые архитектурные компромиссы

### 1. Надежность (Resilience) > Перфекционизм

**Решение:** За 3 дня я выбрал стратегию **defensive programming** вместо feature completeness.

**Что это значит:**
- **Fixed window_size=10** вместо динамического tiktoken → проще, работает в 99% случаев
- **DOM limit 50 элементов** вместо всех 200 → экономия токенов, fallback через scroll
- **Rate limiting 15s** вместо adaptive → защита от 429 даже при API глюках
- **`.first` fallback** при non-unique селекторах → graceful degradation вместо crash

**Альтернатива (почему НЕ реализована):**
```python
# Идеальный вариант потребовал бы:
import tiktoken  # Динамический подсчет токенов
enable_evaluator = True  # Self-critique loop
adaptive_rate_limit = calculate_by_model()  # Умное throttling

# Стоимость: +2-3 дня разработки, +30% сложности кода
# Выигрыш: <5% improvement в edge cases
```

### 2. Token Economy как первоклассный гражданин архитектуры

**Проблема:** Solar Pro free tier = 16k context limit. Один observation на hh.ru = ~1.5k токенов.  
**Без оптимизации:** После 5-7 шагов → context overflow → agent crash.

**Решение:** Каждое архитектурное решение оценивалось через призму "сколько это стоит в токенах":
```python
# Оптимизация #1: Trim conversation history
window_size = 10  # Не все сообщения, а последние 10
# Экономия: ~50k токенов → ~15k токенов на длинной сессии

# Оптимизация #2: Filter DOM elements
elements[:50]  # Топ 50 вместо всех 200
# Экономия: ~20k → ~1k токенов на каждый observation

# Оптимизация #3: Minimize retries
temperature = 0.1  # Детерминированность → меньше ошибок → меньше retries
```

**Результат:** Система сохраняет работоспособность на длинных дистанциях даже при жестком лимите контекста в 16k токенов. Это позволяет агенту выполнять сложные многошаговые задачи без риска аварийного завершения из-за переполнения контекста (context overflow).

### 3. Production-ready код за MVP timeline

**Философия:** Код должен работать не только "у меня на ноутбуке", но и в Docker, CI, у следующего разработчика.

**Что реализовано для production readiness:**
- ✅ **Docker multi-stage build** (non-root user, 450MB вместо 2GB)
- ✅ **CI/CD с matrix testing** (Python 3.10-3.12, security scan)
- ✅ **Graceful error handling** (captcha pause, JSON retry, .first fallback)
- ✅ **Comprehensive docs** (README + docs/ARCHITECTURE; CLAUDE.md — внутренний файл инструкций ИИ-агента, хранится только локально и не входит в публичный репозиторий)
- ✅ **Type safety** (Pydantic models, type hints everywhere)

**Чего НЕТ осознанно:**
- ❌ Evaluator Pattern (self-critique) — это **optimization**, не **requirement** для MVP
- ❌ Автосолвинг капч (2captcha/anti-captcha, audio-challenge + Whisper, solver-расширения) — осознанно НЕ реализуется, не техдолг: капча — барьер доступа, поставленный целевым сайтом; автообход нарушает его ToS, а решение audio-challenge автоматизацией абьюзит accessibility-фичу, предназначенную для людей. Вместо этого: L0 avoidance (`CAPTCHA_AVOIDANCE_MODE` — снижает частоту появления капчи, не решает её) + L2 human-in-the-loop с checkpoint (`./checkpoints/captcha_*.json` сохраняет task/history/context_data/url/step; неблокирующий `run_in_executor` вместо `input()` в event loop; `quit` для graceful-выхода с сохранённым прогрессом).
- ❌ Динамический token counting — KISS principle для 99% сценариев

**Приоритеты:** Фокус на создании стабильного ядра и CI/CD процессов. Дополнительные фичи (Evaluator, Anti-Captcha) вынесены в Roadmap как логическое продолжение развития системы.

### 4. Развитие проекта: четыре новых фичи и честные компромиссы по каждой

После первоначального MVP были добавлены четыре расширения (local providers, обобщение DOM-фолбэков, context compaction, vision fallback). Здесь — та же прозрачность по новым решениям, что и по исходным.

**Local Provider Mode.** Не стал делать «умное автоопределение» локального сервера по URL/порту — раньше именно такая эвристика (специфичный порт Ollama) была источником проблемы, которую просили исправить. Вместо этого — явный флаг `LLM_PROVIDER_MODE`, который либо оставляет прежние облачные проверки как есть, либо полностью их обходит. Плюс: предсказуемо, не ломает cloud-путь ни при каких значениях. Минус: пользователю нужно один раз явно выставить флаг, а не «просто заработает» при указании локального URL — это осознанный trade-off в пользу предсказуемости над удобством.

**Обобщение DOM/click-фолбэков.** Список селекторов для закрытия cookie-баннеров — конечный и основан на самых частых паттернах (OneTrust, типичные фразы accept/agree на нескольких языках), а не универсальный детектор произвольных модалок. Расширять его до полноты — отдельная, потенциально бесконечная задача; выбрал покрыть частые случаи вместо попытки решить общую проблему «найди и закрой любой оверлей».

**Context Compaction.** Сознательно heuristic-триггер (число сообщений / грубая оценка токенов), а не токенайзер конкретной модели — тот же аргумент, что и в разделе про Token Economy выше: точность не стоит добавленной зависимости и сложности для 99% сценариев. Компакция стоит одного дополнительного LLM-вызова — на коротких сессиях (где триггер вообще не срабатывает) это бесплатно, на длинных — оправданная цена за то, чтобы не терять факты о задаче.

**Vision Fallback.** Самый дорогой из четырёх путей по времени и токенам, поэтому единственный, у которого включение требует **двух** независимых флагов (`ENABLE_VISION_FALLBACK` и `MODEL_SUPPORTS_VISION`), а не одного — так сложнее случайно включить его на модели, которая не умеет работать с изображениями, и он остаётся действительно редким фолбэком, а не тихой заменой основного текстового режима.

### 5. Итерация «личный инструмент»: персистентность, LLM-failover, реальные smoke-тесты

Три доработки под сценарий «один оператор на своём сервере». По каждой — что выбрано и от чего отказался.

**Задача 1: SQLite вместо in-memory dict.** Решение: `app.state.tasks` остался горячим in-memory рабочим набором (worker и pub/sub мутируют записи синхронно), но теперь это **write-through кэш** над `aiosqlite`-хранилищем (`src/api/task_store.py`): каждая мутация зеркалится в диск (горячие step-события — fire-and-forget, смены состояний queued→running→finished и stop — через `await`, чтобы терминальное состояние было durable даже при мгновенной смерти процесса), а на старте хранилище гидрируется обратно; задачи, застрявшие в queued/running на момент смерти прошлого процесса, честно помечаются `InterruptedByRestart`. TTL/ретеншн перенесён из констант в Settings (`task_db_path`, `task_ttl_hours`, `max_finished_tasks`, `task_prune_interval_seconds`) и работает и по памяти, и по таблице. Альтернативы: **Redis** — отклонён: внешний сервис, память, пароль, бэкапы ради одного файла данных для одного оператора — чистый оверинжиниринг. **Полноценный ORM/Alembic** — отклонён по той же причине: `CREATE TABLE IF NOT EXISTS` + `INSERT OR REPLACE` + raw SQL покрывают все потребности схемы из одной таблицы, а миграционный фреймворк добавил бы слой сопровождения без единой выгоды на этой стадии. Сознательные минусы решения: SQLite не переживёт одновременную запись из нескольких процессов (не сценарий), а fire-and-forget запись шагов означает, что последние step-события перед крахом могут не доложиться в БД — терминальный результат при этом гарантирован, что для истории запусков достаточно.

**Задача 2: health-check + fallback для LLM.** Решение: опциональный резервный провайдер (`LLM_FALLBACK_PROVIDER_MODE/BASE_URL/API_KEY/MODEL`, всё-или-ничего — половинная конфигурация отвергается на старте, потому что ломается именно в момент аварии). Триггер — **только connection-level ошибки** первичного провайдера (timeout / connect error / APIConnectionError); 429 сознательно НЕ триггерит failover — rate limit транзиентен по своей природе, и переключение провайдера замаскировало бы ошибку pacing-конфигурации вместо её исправления. Перед переключением лёгкий пинг `GET /models` (любой HTTP-ответ = жив, транспортный сбой = мёртв); сам переезд едет на существующем tenacity-retry `generate_action/generate_text` — попытка 1 падает на primary, попытки 2–3 идут уже на fallback, никакого нового слоя ретраев. Переключение sticky (без автопереключения назад — нет ping-pong между двумя флапающими серверами) и ограничено бюджетом `LLM_FALLBACK_MAX_SWITCHES` плюс cooldown после неуспешного health-check'а. Плюс сохранён принцип «явный флаг, не автоопределение по URL/порту» — см. раздел 4. Альтернатива: **постоянный health-check по расписанию** (фоновый пингер обоих провайдеров каждые N секунд) — отклонён: лишний фоновый трафик и состояние «здравый сейчас / мёртв через 5 секунд», тогда как фактическая проверка в момент реального сбоя дешевле и точнее. Ещё одна альтернатива — **автоматический fallback и обратно** (вернуться на primary, когда тот ожил) — отклонена: это и есть механизм ping-pong; возврат на primary — осознанное действие оператора (рестарт процесса).

**Задача 3: дымовые тесты с реальным браузером.** Решение: отдельный модуль `tests/test_real_browser_smoke.py` с маркером `real_browser`, исключённым из прогона по умолчанию через `addopts = -m "not real_browser"` в pyproject (CLI `-m real_browser` его перекрывает). Запускает настоящий Chromium через `BrowserService` против **локального** набора страниц на in-process asyncio-сервере — не example.com/httpbin: внешняя сеть в тестах = flaky по определению. Покрыто: запуск+навигация+title, live-DOM extraction+клик с реальным onclick, заполнение+сабмит формы с проверкой, что сервер увидел именно те данные, корректное закрытие (все handles None + повторный запуск на том же persistent-профиле — zombie-Chromium держал бы lock профиля и упал бы именно здесь). Польза доказалась сразу: тесты поймали два реальных поведения, невидимых для моков — требование blank-line (`\r\n\r\n`) конца HTTP-заголовков и нативную HTML5 constraint-validation, молча блокирующую submit формы с `type="email"` при невалидном значении. Альтернативы: **внешние сайты (example.com/httpbin)** — отклонены: зависимость от чужой доступности и вёрстки делает тест ненадёжным сигналом. **Запуск real-browser на каждый PR в общем CI** — отклонён: браузерный джоб самый флаковый и медленный; сделан отдельным workflow `.github/workflows/real-browser.yml` по недельному расписанию (+ ручной запуск), с `continue-on-error=true` на период обкатки — та же политика, что у существующего e2e-джобы.

### 6. Публичный сервис: санитизация входящих задач

**Задача 4.** Решение: слой политики на приёме (`src/infrastructure/task_policy.py`, вызывается в `POST /task` до постановки в очередь). Всегда включена только гигиена ввода: верхний предел длины (`TASK_MAX_LENGTH`, дефолт 10000), пустой/пробельный текст, управляющие символы кроме `\t\n\r`, отсутствие единственного алфавитно-цифрового символа («`...!!!`» отклоняется до того, как сожжёт LLM-вызов). Контент-фильтр — **отдельный opt-in** (`ENABLE_TASK_CONTENT_FILTER`, по умолчанию выключен): список regex-паттернов целиком из настроек (`TASK_FORBIDDEN_PATTERNS`, построчно), ничего не захардкожено; битый regex оператора пропускается с warning, а не роняет приём. Каждое отклонение пишется в **отдельный JSONL-аудит** (`TASK_AUDIT_LOG_PATH`) с правилом, tenant_id и превью 200 символов (полный вредоносный текст в аудит сознательно не складывается) — отдельно от agent.log, чтобы фильтрацию можно было ревьюить, не грепая смешанные логи; недоступность файла аудита деградирует в обычный лог, но никогда не блокирует API.

Альтернативы: **AI-модерация отдельным LLM-вызовом** — отклонена: стоимость и задержка на КАЖДУЮ подачу ради угрозы-модели («очевидно злоупотребительные формулировки»), которую закрывает статический фильтр; честное ограничение задокументировано вместо дорогого полумера. **Хардкод-список запрещённых слов** — отклонён: у оператора одиночного инстанса и публичного сервиса разные представления о запретном; хардкод гарантированно даёт ложные срабатывания на чужих легитимных задачах и его нельзя выключить без правки кода. Осознанный минус решения: regex-фильтр тривиально обходится перефразированием — это базовая защита от очевидных злоупотреблений, НЕ модерация; для реального публичного сервиса нужен классификатор и/или человеческий ревью (зафиксировано в README.md и ARCHITECTURE.md). Ложные срабатывания проверены тестами: типовые формулировки задач проекта (hh.ru-вакансии, формы, извлечение цен, кириллица, переносы строк/табы) проходят и с выключенным, и с включённым-но-пустым фильтром.

### 7. Публичный сервис: многопользовательская модель

**Задача 1.** Решение: `tenant_id` — опциональное поле `TaskSubmission` с дефолтом `"default"` (полная обратная совместимость: существующие клиенты, UI и тесты работают без изменений), валидация `^[A-Za-z0-9_-]{1,64}$` — id становится сегментом пути профиля и меткой в логах/метриках. Изоляция браузера — `TenantContextPool` (`src/infrastructure/browser.py`): по одному `launch_persistent_context` на тенанта с профилем `{USER_DATA_DIR}/tenants/{tenant_id}/`; выбран именно persistent-контекст (а не один Chromium с `browser.new_context()`) потому, что только он даёт cookies/localStorage, переживающие рестарт процесса — в этом смысл изоляции. Цена осознанная: ~100–300МБ RAM на ОТКРЫТЫЙ контекст; лимит `MAX_CONCURRENT_TENANT_CONTEXTS` (дефолт 1 = прежнее строго последовательное поведение) + закрытие неактивных контекстов по TTL (`TENANT_CONTEXT_IDLE_TTL_SECONDS`, дефолт 600) фоновым свипером; при достижении лимита выселяется наименее давно использованный НЕзанятый контекст (профиль остаётся на диске — сессии не теряются), занятый запущенной задачей неприкосновенен. Контекст тенанта эксклюзивен (Playwright физически не даёт два persistent-контекста на один user_data_dir): задачи одного тенанта выполняются строго последовательно. Очередь заменена с одной общей на **FIFO per tenant + round-robin диспетчер**: 50 задач тенанта A больше не отодвигают задачу тенанта B в конец. Эндпоинты чтения/остановки фильтруются по query-параметру `tenant_id` (дефолт `"default"`, чужая задача = 404, не 403 — не раскрываем существование чужих task_id); `tenant_id=all` — операторский обход фильтра.

Альтернативы: **общий Chromium + new_context()** — отклонён: нет персистентности профилей между рестартами (главное требование), а экономия памяти достигается дешевле через TTL-закрытие. **Общая очередь с приоритетами** вместо round-robin — отклонена: приоритеты требуют политики «чей запрос важнее», round-robin честен по построению и не настраивается вообще. **tenant_id из токена аутентификации** — вне скоупа сознательно: аутентификация — отдельная задача; сейчас tenant_id — это идентификатор бакета ресурсов, НЕ удостоверение личности, и это задокументировано у поля модели. Осознанные минусы: параллелизм ограничен числом открытых контекстов (каждый — отдельный процесс Chromium), а отсутствие аутентификации означает, что любой клиент может назваться любым tenant_id — приемлемо для доверенной сети/reverse-proxy с авторизацией, опасно для голого интернета (DEPLOYMENT.md это фиксирует).

### 8. Публичный сервис: rate-limiting и учёт использования

**Задача 2.** Решение: `src/infrastructure/usage.py::UsageTracker` — in-memory счётчик per tenant с тремя видами лимитов: одновременные запущенные задачи (считаются из живых записей задач на стороне API — нулевой дрейф при падении воркера), скользящее окно подач (`RATE_LIMIT_TASKS_PER_HOUR`, дефолт 60, окно час) и опциональный жёсткий токен-бюджет (`TENANT_TOKEN_BUDGET`, дефолт 0 = выключен). Превышение = HTTP 429 с машинным телом `{error, reason, retry_after_seconds}` и заголовком `Retry-After` — никогда не тихий отказ. Отклонённая подача НЕ расходует квоту: `check_submission()` чистый, `record_submission()` вызывается только после реального принятия. Токены агрегируются по завершении задачи из уже существующего `TaskResult.tokens_used` (тот же источник, что у per-run отчётов), плюс оценка стоимости через информационный `TOKEN_COST_PER_1K_USD`; просмотр — `GET /usage/{tenant_id}` (задачи в окне, lifetime-итоги, токены, стоимость, действующие лимиты).

Альтернативы: **Redis / персистентный счётчик** — отклонён: масштаб «один процесс, несколько известных тенантов»; рестарт сбрасывает окно — честная цена отказа от Redis, а lifetime-токены восстановимы из SQLite-истории задач при необходимости. **Скользящее окно на SQLite** — отклонено в этой же логике: синхронная запись на горячем пути приёма ради счётчика, который не обязан быть durable. **Бюджет календарного месяца** — отклонён: требует персистентности и семантики сброса (UTC? локальная зона?), далёкий от MVP; реализован process-lifetime бюджет с явной пометкой этого ограничения в описании настройки. Осознанные минусы: жёсткий бюджет списывается постфактум (задача, перешедшая лимит, уже потратила токены к моменту учёта — блокируется только СЛЕДУЮЩАЯ подача), а `/usage/{tenant_id}` без аутентификации показывает потребление любого названного тенанта — тот же класс ограничений «идентификатор ≠ личность», что и в задаче 1.

### 9. Публичный сервис: observability

**Задача 3.** Решение: `GET /metrics` в формате Prometheus (`src/infrastructure/metrics.py`): `cogniweb_tasks_total{tenant_id,state}` (переходы queued→running→finished/failed по тенантам), `cogniweb_task_duration_seconds{tenant_id}` (гистограмма), `cogniweb_llm_errors_total{kind}` (timeout/connect/api_connection/rate_limit/api_error — хуки воткнуты в единственную точку маппинга ошибок `_chat_completion`, а не размазаны по коду), `cogniweb_browser_contexts_open` (gauge из пула контекстов). `prometheus_client` — опциональная зависимость по образцу проекта: без пакета все observe-вызовы — no-op, а `/metrics` честно отвечает 503 вместо пустой страницы, притворяющейся, что всё измеряется. `/health` переработан в структурный статус `{status: ok|degraded|down, components: {api, llm, browser, store}}`: LLM — лёгкий пинг `GET /models` активного провайдера (тот же контракт «любой HTTP-ответ = жив», что у failover), browser — состояние пула (все контексты закрыты по TTL = healthy, не down), store — наличие SQLite-хранилища; без production wiring компоненты честно пишут `unknown`, а не фейковый `ok`; `down` = HTTP 503 для алертов. Пробы кешируются на 30 секунд — скрейпер с интервалом 5s не превращается в load-генератор против провайдера. Sentry — строго opt-in: активируется только при заданном `SENTRY_DSN` И установленном `sentry-sdk`, трейсинг выключен (`traces_sample_rate=0.0`) — отправляются только необработанные исключения. Пример `prometheus.yml` и гайд «что смотреть» — `docs/MONITORING.md`.

Альтернативы: **pull vs push (StatsD)** — выбран pull: Prometheus де-факто стандарт, push потребовал бы шлюза. **Полноценный browser-probe с запуском Chromium на каждый health-check** — отклонён: запуск процесса ради liveness дороже самого сервиса; состояние пула + факт жизни Chromium-процессов достаточны, глубокая проверка покрыта real-browser smoke-тестами. **Sentry из коробки с DSN-заглушкой** — отклонён: телеметрия наружу должна включаться явно оператором, не молча. Осознанные минусы: `/metrics` открыт без bearer-токена (скрейпер внутри доверенного периметра; лейблы tenant_id — клиентские идентификаторы, не секреты) — при экспозиции порта наружу закрывать на reverse-proxy (описано в docs/MONITORING.md); гистограмма с лейблом tenant_id растёт кардинальностью с числом тенантов — приемлемо для единиц тенантов, для сотен потребуется ревизия.

### 10. Публичный сервис: документация по продакшен-деплою

**Задача 5.** Решение: `docs/DEPLOYMENT.md` для читателя, уже прошедшего QUICK_START.md — без дублирования установки; провайдер-агностично («любой VPS с Ubuntu»). Покрыты все пункты ревью: nginx с WebSocket-upgrade (WS `/ws/task/{id}` реально используется UI — конфиг без `Upgrade`/`Connection` заголовок сломал бы живой стрим, это отражено явно), certbot + автопродление, systemd-юнит с `Restart=on-failure`, `KillSignal=SIGTERM` и щедрым `TimeoutStopSec` — потому что SIGTERM в приложении означает drain (текущая задача доходит до границы шага, и убивать её жёстко значило бы обесценить graceful-shutdown, который строился раньше); таблица продакшен-переменных с разделением «обязательно переопределить» (`API_AUTH_TOKEN`, пути данных) / «безопасный дефолт» (`API_BIND_HOST=127.0.0.1` — наружу только nginx); раздел бэкапов — реализованный SQLite через `sqlite3 .backup` (онлайн-консистентная копия при живом писателе, без остановки сервиса) + предупреждение о чувствительности профилей браузера (= сессии аккаунтов). Плюс финальный чеклист проверки деплоя.

Альтернативы: **docker-compose как основной путь деплоя** — отклонён в пользу «голого» systemd: на одиночном VPS compose добавляет слой отладки без выигрыша, а Dockerfile/MODE=api задокументированы ранее и упомянуты как вариант (с важной поправкой про `-p 127.0.0.1:...`). **Инструкция под конкретного облачного провайдера** — отклонена по требованию и по существу: различия между AWS/GCP/Hetzner не влияют ни на один шаг этого документа. Осознанное ограничение документа: это справочник по умолчанию-безопасной конфигурации, а не по безопасности как таковой — аутентификация tenant_id, ротация токенов, WAF остаются вне скоупа и помечены как таковые.
